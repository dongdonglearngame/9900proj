\section*{Executive Summary}
\addcontentsline{toc}{section}{Executive Summary}

We built a local web tool for studying how a small open-source language model answers
emotional-reasoning questions from EmoBench \cite{sabour2024}. A user loads a scenario,
sees the model's answer, chooses a different answer (we call it the \emph{foil}), and
runs a search strategy that tries to change the model's answer to that foil by editing
only the scenario text. This follows the general idea of counterfactual explanations:
show the smallest change to the input that changes the output
\cite{wachter2018,miller2019}.

The system contains a simple word-level baseline and three main counterfactual
strategies: \stratone{}, \strattwo{}, and \stratthree{}. All four run against the same
frozen target model through the same verification path, so their results can be
compared fairly.

We do not treat every answer change as a good explanation. The finished system
separates a \emph{mechanical flip} (the model changed its answer) from a
\emph{human-valid explanation} (reviewers agree the edit is a meaningful change), a
\emph{diagnostic finding} (the model reacted to wording, spelling, or a leaked answer
cue), and a valid \texttt{not\_found} result (no flip within the budget). This
distinction became central after our Sprint 2 experiments showed that a higher flip
rate can also mean larger, contradictory, or unhelpful edits.

In Sprint 3 we added a shared minimality stage and a fluency check, built a
discovery-focused variant of each main strategy, clarified the result labels in the
interface, and added accessibility settings. This report explains the final design,
shows the measured results, includes example outputs of good and bad quality, and
states clearly which goals were met and which were not. We present every flip as
evidence of model behaviour under a frozen test setup, not as proof of the model's
internal reasoning.

\section{Installation Manual}

The application is dockerised. Docker Compose builds and starts the backend (FastAPI)
and the frontend (React build served by nginx). Ollama stays on the host machine
because it manages the local language models; the project deliberately uses no paid
cloud API. The exact Python, Node, and package versions are pinned in the repository
(\texttt{backend/requirements.txt}, \texttt{frontend/package-lock.json}) and are listed
in the repository README, so the report only describes the steps to run.

\subsection{Prerequisites and Setup}

The machine needs Docker Desktop (or Docker Engine with Compose), Ollama, and the two
EmoBench data files (\texttt{EU.jsonl}, \texttt{EA.jsonl}), which are supplied
separately because the benchmark data is not committed to Git.

\begin{lstlisting}[style=terminal,language=bash]
# 1. Clone the repository and enter it
git clone https://github.com/unsw-cse-comp99-3900/capstone-project-26t2-9900-f09c-almond.git
cd capstone-project-26t2-9900-f09c-almond

# 2. Start Ollama on the host and pull the frozen local model
ollama pull llama3.2:3b

# 3. Place EU.jsonl and EA.jsonl in data/raw/

# 4. Build and start the application
docker compose up --build -d

# 5. Load the EmoBench data into SQLite (one-off)
docker compose exec backend python -m app.scripts.load_emobench \
  --input /data/raw/EU.jsonl
docker compose exec backend python -m app.scripts.load_emobench \
  --input /data/raw/EA.jsonl
\end{lstlisting}

The frontend is then available at \url{http://localhost:5173} and the backend API
documentation at \url{http://localhost:8000/docs}. \texttt{docker compose down} stops
the application. The named SQLite volume preserves imported scenarios,
target-prediction cache entries, experiment-run metadata, and job checkpoints across
container restarts. Completed counterfactual payloads, metrics, and batch-comparison
results are currently retained in process memory and must be rerun after a backend
restart. For development without Docker, the README also documents the manual path
(Python 3.11 virtual environment plus \texttt{npm run dev}).

\subsection{Major Components and Data Flow}

\begin{enumerate}
  \item The user selects an EmoBench scenario and the local model in the React
  interface.
  \item The backend asks the frozen target harness for the original answer. The target
  prompt is stateless and deterministic, and it never contains the foil.
  \item The user selects a foil and one strategy (Baseline, Strategy 1, Strategy 2, or
  Strategy 3, each with a strict or discovery variant where available).
  \item The strategy proposes scenario edits in its own way. Only the frozen target
  decides whether a candidate reaches the foil.
  \item A successful candidate then passes through shared minimality, fluency scoring,
  and risk labelling before metrics are retained in process memory and displayed.
  \item A search that uses up its budget without a flip is stored as
  \texttt{not\_found}. It is not turned into an error, and no explanation is invented.
\end{enumerate}

Because every strategy shares the same target function, prompt version, success rule,
budgets, and metric definitions, differences between strategies can only come from how
they search. That is what makes the comparison fair.

\section{Design Justifications}

The system was designed to support a controlled comparison of counterfactual search
strategies, not to maximise the number of answer flips. That objective forced three
commitments, which this chapter justifies in turn: every strategy must face the same
frozen judge (Section~\ref{sec:harness}); the strategy families must embody
genuinely different search hypotheses rather than variants of one prompt
(Section~\ref{sec:strategies}); and every published result must pass through the
same shared quality stages without being promoted to a valid explanation by the
software alone (Section~\ref{sec:quality}). Section~\ref{sec:terms} first defines
the outcome levels these commitments protect. For each decision we state the risk it
controls, the alternative we considered, the evidence behind it, and the limit of
what it can guarantee. The numeric settings quoted in this chapter (the 0.60
changed-fraction cap, the 0.75 fluency threshold, the three-flip retention limit,
and the overbroad-span rule) are operational settings chosen during development, not
calibrated constants. The design itself was not fixed up front:
Table~\ref{tab:evolution} summarises how experiments and client and tutor feedback
moved it from finding any verified flip (Sprint~1), to bounding and instrumenting
the search (Sprint~2), to separating search coverage from explanation quality
(Sprint~3).

\subsection{Design Criteria and Outcome Taxonomy}
\label{sec:terms}

The first design decision is about vocabulary: what the system is allowed to call
success. A user picks a \textbf{foil} --- the alternative answer they want the model
to give; the strategy may know it, but the target model is never shown it. When an
edit makes the frozen target's answer equal the foil exactly, we call that a
\textbf{mechanical flip}. The criterion at the centre of the design is that a
mechanical flip is \emph{necessary} for a counterfactual explanation but not
\emph{sufficient}: it says the answer changed, not that the edit is a meaningful
account of why. Under one undifferentiated ``success'' label, an answer leak would
be indistinguishable from a genuine event change, and every aggregate number in
Section~4 would inherit that ambiguity. The automated system therefore assigns each
run exactly one outcome category (Figure~\ref{fig:taxonomy}):

\begin{itemize}
  \item \textbf{Mechanical flip -- review needed.} A publishable primary flip was
  found: it reaches the foil and survived the deterministic risk checks. Its quality
  is still unestablished.
  \item \textbf{Diagnostic finding.} Every verified flip in the run was risk-flagged
  --- for example a near-synonym swap or an answer leak. These are kept as evidence
  about the model's sensitivities and never published as explanations.
  \item \textbf{Not found.} No verified flip within the budget. This is a real
  research result about model stability, not an error, and no explanation is
  invented for it.
  \item \textbf{Failed.} An infrastructure fault, reported separately so it is never
  confused with a scientific outcome.
\end{itemize}

Underneath the run category, each individual verified flip is classified
\emph{primary} or \emph{diagnostic} by the same deterministic checks, so a run whose
only flips were risk-flagged is reported as a diagnostic finding, not as a success.
A third level lies outside the software entirely: \textbf{semantic validity},
whether the edit meaningfully changes the situation --- an event, outcome,
relationship, or observable behaviour --- rather than exploiting a trick. Reviewers
label each surviving flip Good, Acceptable, or Invalid with reason codes under the
external blinded protocol of Section~\ref{sec:review}; the automated pipeline can
only mark a flip as awaiting that review, never assign the label itself.

Three further quantities are \emph{measurements} attached to a result; they describe
a flip, and none of them adjudicates it.

\begin{itemize}
  \item \textbf{Minimality.} The word-level edit distance between the original and
  edited scenario (single-word insertions, deletions, and replacements), plus the
  changed-word fraction (that count divided by scenario length). Smaller is better,
  because a small change is easier for a person to read and reason about.
  \item \textbf{Fluency.} Whether the edited text still reads as natural English,
  scored automatically by a local judge model (Section~\ref{sec:quality}). The
  score is a proxy, not proof.
  \item \textbf{Budget.} The maximum number of target-model checks one strategy may
  use for one scenario. Search and post-processing each have a capped allowance, and
  all counts are recorded, so no strategy can look cheap by hiding work.
\end{itemize}

A result can score well on every measurement and still be worthless as an
explanation: a two-word, fluent edit that quietly copies the answer into the text is
minimal, fluent, and invalid. The boundary is not hypothetical. In the one fully
reviewed run (Section~\ref{sec:review}), all four published flips were verified,
fluent, and moderately sized, and human reviewers still judged all four Invalid.
That result is the empirical justification for keeping the automated categories and
the human judgement separate.

\subsection{Frozen Target Harness: One Judge for Every Strategy}
\label{sec:harness}

The threat this decision controls is confounding on the judge's side. Strategies are
compared by how often and how cheaply they flip the target, so if each strategy
could call the target with its own prompt, decoding settings, or answer parser, an
observed difference could come from the prompt rather than from the edits, and the
comparison would measure strategy-plus-prompt bundles instead of search procedures.
We considered the permissive alternative --- letting each strategy tune its own
target prompt, which could raise individual flip rates --- and rejected it, because
the project's question is which \emph{search procedure} finds better
counterfactuals, not which prompt makes the model easiest to move. The harness
fixes the following invariants for every call by every strategy:

\begin{itemize}
  \item the target receives only the scenario and the choices --- never the foil,
  the ground truth, or any strategy information;
  \item one pinned target prompt version
  (\texttt{target-v2-chat-dynamic-choices}, Appendix~\ref{app:prompts}), decoding
  configuration, answer parser, and cache contract for all strategies;
  \item one success rule: a flip is exactly \texttt{prediction.answer == foil};
  \item capped, recorded call budgets for search and post-processing.
\end{itemize}

The proposer LLM, by contrast, may see the foil. This is a deliberate asymmetry of
roles: the proposer generates candidates and proves nothing, while the foil-blind
target check alone decides. The guarantee must also be stated at its true strength:
freezing the target prompt, decoding, parser, and cache \emph{reduces} target-side
confounding, so observed differences more directly reflect the search procedures
under the stated runtime conditions. It does not remove every source of variance ---
the proposer samples at temperature 0.7 and is not bit-for-bit repeatable --- which
is why Section~4 reports paired same-job comparisons (Sections~\ref{sec:s1results}
and~\ref{sec:s3results}) and treats the single-run runtime table
(Section~\ref{sec:runtime}) as an illustration of cost scale, not a ranking.

\subsection{Strategy Families and Search Trade-offs}
\label{sec:strategies}

A fair arena is pointless if all contestants are alike. The four implemented
families cover progressively more structured units of change --- a fixed word list,
a free event-level rewrite, an importance-guided span infill, and a single grounded
concept intervention --- so the comparison tests different hypotheses about where
useful counterfactuals can be found, not four variants of one prompt. The client
asked us to number the strategies clearly, so the report uses Strategy~1--3 plus the
Baseline; the internal code identifiers differ (the \texttt{s1}, \texttt{s2},
\texttt{s4}, and \texttt{s6} families respectively), and Appendix~\ref{app:mapping}
maps every report name to its code identifier and pinned prompt versions.
Figure~\ref{fig:flows} shows the search flow of each family.

One scope change must be stated first. The proposal planned six strategy families
(internal identifiers S1--S6). The delivered and evaluated release implements four:
S1 (the Baseline), S2 (Strategy~1), S4 (Strategy~2), and S6 (Strategy~3), each main
family in a strict and a discovery variant. The control-code family (S3) and the
population-based search family (S5) were not implemented, no result in this report
uses them, and they remain future work (Table~\ref{tab:future}). We judged the
delivered four sufficient for the design goal, because they already span the
edit-unit spectrum from single words to whole-event rewrites.

\paragraph{Baseline: word-level greedy search (code family \texttt{s1}).}
Every comparison needs a floor that establishes what purely mechanical local editing
achieves. The Baseline tries word and phrase substitutions from a fixed list --- no
LLM generates candidates --- and verifies each attempt. It is transparent, cheap,
and deterministic, so it shows how much of an LLM strategy's advantage survives
against the simplest competitor. Its known limit is expressive: it cannot produce a
coherent event-level change, which is the gap the main strategies exist to close.

\paragraph{\stratone{} (code family \texttt{s2}).}
A fixed substitution list cannot express ``the outcome of the event was
different''. Here a local proposer LLM reads the scenario, choices, and foil, and
proposes complete rewrites that change one event, outcome, relationship, or
observable behaviour; deterministic guards reject rewrites that break structure,
leak the answer, or change too much, and the frozen target verifies the survivors
(following the zero-shot direction of \cite{bhattacharjee2024} with our target
frozen). The expected advantage is a much richer candidate space; the accepted
trade-off is that the same freedom creates the leak, contradiction, and over-editing
failure modes --- which is why the guards and the diagnostic route exist. The strict
variant prefers about three and at most six changed words; the discovery variant
removes the fixed cap under a 0.60 changed-fraction safety cap, retains up to three
distinct verified flips, and sends the best one to the shared quality pipeline. Its
measured behaviour is reported in Section~\ref{sec:s1results}.

\paragraph{\strattwo{} (code family \texttt{s4}).}
Strategy~1 still guesses where to edit. This family asks the target itself what
matters: it occludes one span at a time, ranks spans by how the frozen target's
confidence shifts, then has the proposer LLM infill the most important spans ---
adapting importance-guided contrastive editing \cite{ross2021} to a black-box
setting without gradients. When no usable confidence values are exposed, the ranking
falls back to an answer-change heuristic and that coverage is reported, not silently
zero-filled. The expected advantage is that a limited budget concentrates on spans
the target is demonstrably sensitive to; the structural cost is that probes spend
target calls before any candidate exists, visible in the runtime table
(Section~\ref{sec:runtime}). Evidence status: both variants are implemented,
unit-tested, and completed a real-model smoke run, but their paired comparative
evaluation was not completed within the term, so the expected advantage remains a
design hypothesis rather than a measured result (Strategy~2 status, Section~4).

\paragraph{\stratthree{} (code family \texttt{s6}).}
Even a well-placed span edit tells a person which \emph{text} mattered, not which
\emph{situational factor} mattered. This family changes exactly one concept ---
time, place, relationship, urgency, or outcome. The proposer must point to one exact
text span and a replacement; our code checks the span occurs exactly once and
applies the edit deterministically, so the LLM never rewrites the whole story
(inspired by concept-level work \cite{gat2024}). We call it \emph{causal-inspired}
deliberately: changing one concept and observing the model is an intervention on the
text, not proof of real-world causality. The expected advantage is a human-legible
unit of explanation; the trade-off is that concept boundaries are proposed by an LLM
and can be too broad, so the discovery variant --- which adds an outcome concept
class and allows a coherent multi-word replacement span --- demotes overbroad spans
(at least 12 tokens and more than half the scenario) to diagnostic findings. Its
measured behaviour on a frozen, unenriched set is in Section~\ref{sec:s3results}.

\paragraph{Strict versus discovery: one conflict, resolved once.}
The variant split records a design conflict and its resolution, not version
history. Sprint~2 exposed both horns: a broad prompt found many flips with large
edits, while the strict word cap recovered small edits by rejecting most of the
coverage (Table~\ref{tab:prelim}). The cap was doing minimisation's job in the wrong
place --- discarding coherent event-level candidates before the shared minimiser
could see them. The discovery variants move that responsibility downstream:
strategies search more broadly under bounded budgets and safety caps, and the shared
pipeline shrinks, scores, and classifies whatever survives. The paired dev-40 run
confirmed the intended trade --- substantially broader coverage at a higher raw
edit-size and call cost, with shared minimality then halving both variants' edits
(Table~\ref{tab:s1}, discussed in Section~\ref{sec:s1results}). The strict variants
remain the default and the comparison baseline; keeping both is what makes the
Sprint~3 change auditable rather than merely asserted.

\subsection{Shared Quality Pipeline and Evidence Boundaries}
\label{sec:quality}

If each strategy minimised, polished, or scored its own results, a strategy could
look better simply by grading itself leniently --- the confound of
Section~\ref{sec:harness}, moved downstream. The pipeline therefore takes the
selected primary flip of every strategy through the same fixed stages: minimality,
fluency scoring with one bounded polish, then risk flags, metrics, and external
human review; diagnostic flips bypass the publishable route and are retained as
sensitivity evidence. One rule governs re-verification: every stage that changes the
scenario must re-verify the flip through the frozen target, while stages that only
score, classify, or record make no further target call.

\paragraph{Minimality (greedy restoration).}
The minimiser aligns the original and edited text, finds the changed regions, and
repeatedly tries to restore original content, first clause by clause, then word by
word, re-checking the frozen target after each restoration: if the answer is still
the foil the restoration is kept, otherwise it is rolled back. It stops when nothing
more can be restored or the post-processing call cap is reached. The result is a
verified local minimum, not a guaranteed global one. The edit distance before and
after is recorded and both texts stay visible, because a smaller edit can hide that
the original mechanism was weak.

\paragraph{Fluency (scored proxy).}
A separate local judge (the same \texttt{llama3.2:3b} model with a fixed rubric
prompt at temperature 0, version \texttt{fluency-judge-v2-rubric-100}; the full
rubric is in Appendix~\ref{app:prompts}) reads only the edited scenario --- no
choices, no foil --- and returns an integer score stored as
$\text{judge integer}/100 \in [0,1]$. A fluency assessment is marked as passing when
the stored score is at least 0.75. This flag describes readability only: it does not
establish semantic validity, and a low or missing score does not by itself suppress
an already verified flip. If the judge fails or returns invalid output, we store
\texttt{not\_measured} with a reason instead of inventing a value. The score is a
proxy with documented errors in both directions: Section~\ref{sec:qualitative} shows
one broken sentence the judge correctly caught at 0.62 and another it wrongly passed
at 0.83, which is one reason human review remains mandatory.

\paragraph{One constrained polish.}
If the fluency score is low, the pipeline may attempt exactly one polish,
constrained to deleting unnecessary words from the changed span: it must not add,
replace, reorder, or inflect words, must not increase the edit distance or change
sentence boundaries, and must not introduce option letters, answer wording, or
emotion labels. Because the polish changes the scenario, it is re-verified: it must
score higher than before and still flip the frozen target, otherwise it is rolled
back and the pre-polish verified result stands.

\paragraph{Risk flags and human review.}
Deterministic checks flag high-confidence problems: exact or morphological answer
leakage, option references such as ``answer is C'', near-synonym-only or
surface-form-only changes, focal-person shifts, multi-concept spans, and overbroad
concept spans. Flagged flips become diagnostic findings. Everything that survives
remains only ``mechanical flip, review needed'' until two reviewers, hidden from
each other and blind to strategy identity, label it Good, Acceptable, or Invalid
with reason codes, with disagreements adjudicated. This review is an external
protocol executed outside the application and recorded in the evaluation documents;
the interface displays each surviving flip with its review-needed status, but the
validity labels are assigned only by that protocol. Our own data demonstrates why
the division of labour is necessary: in the one fully exercised review
(Section~\ref{sec:review}), the deterministic rules flagged none of the four
published flips, and the reviewers judged all four Invalid. Minimality and fluency
cannot rescue an invalid edit: a short, grammatical answer leak is still invalid.

\subsection{Result Categories}

We do not use one ambiguous success label. Every completed run is reported as exactly
one of:

\begin{itemize}
  \item \textbf{Valid explanation:} a coherent event, outcome, relationship, or
  behaviour change judged Good or Acceptable by reviewers;
  \item \textbf{Mechanical flip -- review needed:} the target reached the foil, but
  quality has not been established yet;
  \item \textbf{Diagnostic finding:} a verified flip caused by lexical, formatting,
  contradiction, focal-shift, evaluative-cue, or answer-leakage sensitivity;
  \item \textbf{Not found:} no flip within the frozen budget, which is a real research
  result about model stability;
  \item \textbf{Failed:} an infrastructure error, reported separately and excluded
  from the scientific denominators.
\end{itemize}

\subsection{Human Review Evidence}
\label{sec:review}

Blinded dual review is part of the pipeline, and we exercised it fully once during
Sprint 3, on an earlier Strategy 3 run. That run was later found to have a
contaminated control arm (the strict arm had received part of the discovery
configuration), so its strict-versus-discovery comparison is void and the 20 questions

adjudicated. The final labels were 4 Invalid out of 4, with reason codes including

reviewers still judged all four invalid as explanations. Mechanical checks alone are
not enough, which is exactly why the pipeline keeps human review as a separate final
stage.

\subsection{Qualitative Analysis: Good and Bad Examples}
\label{sec:qualitative}

Numbers alone hide what the edits actually look like, so here are real outputs, quoted
from stored artifacts, with our assessment.

\paragraph{Provisionally acceptable (Strategy 1, holdout question 107).}
The original scenario ends ``\ldots the result was \emph{the expected one}.'' The edit
replaces this with ``\ldots the result was \emph{unusually accurate}.'' The model's
answer changed to the foil. The edit changes the real outcome of the event, stays
grammatical, and does not mention any answer text, so the reviewer marked it
provisionally acceptable. This is the behaviour we want the tool to find.

\paragraph{Invalid: near-synonym surface change (Strategy 1, holdout question 132).}
The edit changed one word, ``pale'', to ``green'', in a description of someone's face.
The model flipped, but no fact about the situation changed. This is lexical
instability of the model, so it is recorded as a diagnostic finding about the model,
and marked invalid as an explanation.

\paragraph{Invalid: cue made more explicit (Strategy 3 discovery, evaluation
question 162).}
The edit replaced ``his face squished up'' with ``a look of distaste on his face'',
and the model moved from Embarrassment to Annoyance. The automatic checks flagged
nothing and fluency scored 0.90, but content review found the modified clause is a
sentence fragment, the ``emotional intensity'' concept label does not match what the
replacement actually does, and the change mainly makes an already negative cue more
explicit rather than changing the situation. Provisionally invalid; blinded labels
pending. It is still useful evidence that the model is sensitive to the explicit word
``distaste''.

\paragraph{Pipeline failure caught by the gate (Strategy 1 discovery, dev
question 161).}
Discovery found a coherent raw rewrite: ``It said there is a restaurant famous for its
rude customer service'' became ``She had already heard about the infamous waiters who
often insult customers''. Minimality then reduced the 12-word edit to 2 words, leaving
``She said already is a restaurant famous\ldots'', which is broken English. The
fluency judge scored it 0.62, below the 0.75 threshold, so the failure was caught and
reported. This example is why we keep the raw, minimal, and final versions all
visible.

\paragraph{Pipeline failure missed by the gate (Strategy 1 discovery, dev
question 121).}
On another question, minimisation of a larger rewrite produced ``\ldots Vivian's leg
began shake uncontrollably'', which drops the word ``to'' and is ungrammatical, yet
the judge scored it 0.83 and passed it. This false pass is direct evidence that the
automatic fluency score is a proxy that can be wrong in both directions, and it is one
reason human review remains mandatory.

\subsection{Which Objectives Were Met}

Against the criteria in Table~\ref{tab:criteria}: the functional workflow,
reproducibility, result-category, and accessibility objectives are met and
demonstrated; flip discovery, minimality, and efficiency are measured and reported
with honest caveats; fluency is measured but its reliability is only partly
established (one false pass and one correct catch are documented above); and semantic
validity is the least complete objective, with the dual-review process proven once
end-to-end but the final blinded labels for the newest results still pending. Strategy
2's comparative evaluation was not completed. We expand on these in the limitations.

\section{Limitations and Future Work}

\subsection{Limitations}

\begin{itemize}
  \item \textbf{Small local model.} The default 3B model runs on CPU laptops but has
  limited emotional reasoning, instruction following, and editing ability. Observed
  sensitivities may be specific to this model.
  \item \textbf{Black-box evidence.} A counterfactual shows the output changed when
  the input changed. It does not reveal internal reasoning or prove causality, and we
  label Strategy 3 causal-inspired for exactly this reason.
  \item \textbf{Mechanical versus valid flips.} Minimality and fluency cannot turn an
  answer leak, contradiction, or irrelevant cue into a valid explanation. On the one
  fully reviewed run, all four published flips were judged invalid.
  \item \textbf{Human review scale.} Two-reviewer validity labels exist for one
  consumed run; the blinded labels for the newest Strategy 1 and Strategy 3 flips are
  still pending, so all newer validity statements are provisional.
  \item \textbf{Automatic quality proxies.} The fluency judge false-passed a broken
  sentence (0.83) and the risk rules flagged none of the four human-invalid flips, so
  neither replaces review.
  \item \textbf{Minimality side effects.} Greedy restoration sometimes removes
  connective words and produces fragments; raw and final texts are both kept visible
  to compensate.
  \item \textbf{Incomplete comparisons.} Strategy 2 has only smoke-level evidence, and
  a single all-strategy controlled holdout matrix was not run within the term; the
  per-strategy paired comparisons above use different sets and must not be compared
  against each other.
  \item \textbf{Run variability.} The proposer runs at temperature 0.7 and is not
  bit-for-bit repeatable across local runs even with a fixed seed, so paired
  same-job comparisons are reported and repeated-run variance remains unmeasured.
  \item \textbf{Evaluation scope.} EmoBench is a benchmark, not a clinical setting.
  The tool analyses model behaviour and must not be used to provide mental-health or
  medical advice.
  \item \textbf{Language setting.} The interface language switch translates the
  interface only; translating scenarios would change the input being evaluated.
\end{itemize}

\section{Conclusion}

We delivered a working, dockerised local tool and a controlled way to study
counterfactual editing strategies on emotional-reasoning questions. The main result is
not one high flip rate. It is a reproducible workflow that shows when a frozen model's
answer can be changed, how small and readable the change is, what kind of change it
was, and whether people judge it a useful explanation. On our measurements, discovery
search finds clearly more mechanical flips than the strict Sprint 2 baseline on
development data (25\% versus 10\% for Strategy 1) at a higher edit-size and call
cost, a harder unenriched set yields very few flips for Strategy 3 (1/20), and the one
fully reviewed run showed that verified, fluent, small edits can still all be invalid
as explanations. The honest separation of valid, diagnostic, not-found, and failed
outcomes, kept visible from the code through to the interface, is what makes those
statements trustworthy, and it is the part of this project we would keep first.

\section{Prompt Texts}
\label{app:prompts}

Every prompt sent to an LLM is versioned, and the version string is stored with each
experiment run. The instruction texts below are quoted from the code at the release
commit. Each proposer prompt is accompanied by a JSON user message containing the
scenario, choices, original answer, foil, requested count, and previously failed
attempts; the target and fluency prompts receive only what is shown.

\subsection{Frozen target prompt (\texttt{target-v2-chat-dynamic-choices})}

The system message is built from the actual choice letters (two to six choices are
supported):

\begin{lstlisting}[style=prompt]
You answer multiple-choice emotional reasoning questions. Return only one
letter A, B, C, or D. Do not explain.
\end{lstlisting}

The user message contains only the scenario and the choices. It never contains the
foil, the ground truth, or any strategy information:

\begin{lstlisting}[style=prompt]
Scenario
<scenario text>

Choices
A. <choice text>
B. <choice text>
...

Answer with exactly one letter.
Answer
\end{lstlisting}

\subsection{Strategy 1 strict proposer (\texttt{s2-proposer-v5-\allowbreak coherence-\allowbreak checklist})}

\begin{lstlisting}[style=prompt]
You propose minimal counterfactual rewrites for emotion-reasoning
multiple-choice scenarios. You may see the target foil, but the frozen
target model will not. Change an underlying event, outcome, relationship,
or observable behaviour rather than directly naming or paraphrasing the
target emotion or answer. Modify exactly one existing sentence and do not
append, prepend, split, or merge sentences. Prefer changing no more than
3 words and never change more than 6 words. Preserve the surrounding
facts, actors, tense, grammar, and narrative coherence. Rewrite only the
scenario, keep it fluent and realistic, do not mention option letters,
and do not copy or morphologically derive any option answer text in the
scenario. Do not add a sentence or clause whose purpose is to state how a
person feels; express the change through an observable event, outcome,
relationship, or behaviour. Do not propose an edit that makes unchanged
sentences contradict the modified fact. Keep the changed sentence about
the same focal person or event and preserve at least one meaningful
content word from that sentence. Never replace a focal person's outcome
with a reaction by the crowd or another bystander. Before returning each
rewrite, silently check every unchanged sentence for references to a fact
the rewrite removed. [quality examples omitted for space; they show one
good three-word outcome edit and three bad patterns to avoid]
Return exactly the requested number of distinct rewrites and use a
different change mechanism where possible. Treat avoid entries as prior
failures and do not repeat them. Return JSON only; modified_scenario is
required and changed_span, change_type, and rationale are optional:
{"rewrites":[{"modified_scenario":"...","changed_span":"...",
"change_type":"event|outcome|relationship|behaviour","rationale":"..."}]}.
\end{lstlisting}

\subsection{Strategy 1 discovery proposer
(\texttt{s2-proposer-v8-2-\allowbreak discovery-\allowbreak focused-event})}

\begin{lstlisting}[style=prompt]
You search for counterfactual scenario edits for an emotion-reasoning
multiple-choice task. You may see the target foil, but the frozen target
model will not. Rewrite only the scenario and keep every answer choice
unchanged. Make one focused, coherent change to an underlying event,
outcome, relationship, or observable behaviour that could support the
target answer. Keep the change concise, but do not force it into a fixed
word count when a larger local change is needed for coherence. Return the
complete scenario for every rewrite, not only the changed sentence. Keep
exactly the same number and order of sentences, copy every unchanged
sentence word-for-word, and replace only one existing sentence in place.
Do not append, prepend, split, or merge sentences. Preserve the focal
person, tense, unrelated facts, grammar, and references from unchanged
sentences. Do not state an emotion as a shortcut, mention an option
letter, or copy answer-option wording into the scenario. Treat avoid
entries as prior failures and propose distinct mechanisms where possible.
The rewrites array must contain exactly <count> distinct objects; do not
stop after fewer than <count>. The top-level object must contain only the
rewrites key. Never echo input keys such as scenario, choices,
constraints, count, foil, or avoid. Replace every placeholder in this
exact output shape and return JSON only: {"rewrites":[
{"modified_scenario":"<complete scenario rewrite 1>","changed_span":
"<changed text>","change_type":"event|outcome|relationship|behaviour",
"rationale":"<brief reason>"}, ...]}
\end{lstlisting}

\subsection{Strategy 2 infill proposer (\texttt{s4-infill-v1})}

\begin{lstlisting}[style=prompt]
You fill masked spans in emotion-reasoning multiple-choice scenarios.
You may see the target foil, but the frozen target model will not.
Only replace each [MASK] span. Preserve every unmasked character exactly,
keep the final scenario fluent and realistic, do not mention option
letters, and do not copy any option answer text into the scenario.
Return JSON only:
{"rewrites":[{"modified_scenario":"...","rationale":"..."}]}.
\end{lstlisting}

\subsection{Strategy 3 strict proposer (\texttt{s6-concept-v2-grounded-diverse})}

\begin{lstlisting}[style=prompt]
You propose causal-inspired concept interventions for emotion-reasoning
scenarios. Each edit must change exactly one allowed concept through one
contiguous span replacement while keeping every other fact and concept
fixed. Copy original_span exactly from the scenario. Return only the
replacement, not a rewritten full scenario. Do not mention option letters
or copy any option answer text. Return exactly the requested number of
edits. Within this response, use different concept classes and original
spans where possible. Do not repeat any concept/span/target tuple in
used_edits or avoid. Return JSON only:
{"edits":[{"concept_class":"time","original_span":"...",
"replacement_span":"...","source_value":"...","target_value":"...",
"rationale":"..."}]}.
\end{lstlisting}

\subsection{Strategy 3 discovery proposer (\texttt{s6-concept-v3-discovery-first})}

\begin{lstlisting}[style=prompt]
You propose causal-inspired concept interventions for emotion-reasoning
scenarios. Treat one coherent situational concept intervention, not a
fixed token count, as the unit of change. A multi-word replacement is
allowed when needed to express that one concept clearly. Each edit must
change exactly one allowed concept through one contiguous span
replacement while preserving the focal actor, focal event, and every
unrelated fact. Copy original_span exactly from the scenario. Return only
the replacement, not a rewritten full scenario. Do not mention option
letters or copy any option answer text. Return exactly the requested
number of edits. Prefer unused concept classes and original spans, and do
not repeat any concept/span/target tuple in used_edits or avoid. Return
JSON only: {"edits":[{"concept_class":"time","original_span":"...",
"replacement_span":"...","source_value":"...","target_value":"...",
"rationale":"..."}]}.
\end{lstlisting}

\subsection{Strategy 3 grounding repair (\texttt{s6-concept-repair-v1})}

\begin{lstlisting}[style=prompt]
Repair only the grounding of one causal-inspired concept edit. Return
exactly one edit with an original_span copied verbatim from the scenario
that occurs exactly once. Preserve the supplied concept_class,
replacement_span, source_value, and target_value; do not invent a
different intervention or rewrite the full scenario. Do not mention
option letters or copy answer text. Return JSON only in the same edits
schema.
\end{lstlisting}

\subsection{Minimality span shrink (\texttt{postprocess-\allowbreak inserted-span-\allowbreak shrink-v2})}

\begin{lstlisting}[style=prompt]
Reduce one inserted span by deleting unnecessary words only. Keep the
remaining words in their original order; do not paraphrase or add any new
word or fact. Do not rewrite the rest of the scenario, mention option
letters, name the target answer, or add emotion labels. Return JSON only
with exactly one rewrite whose original_span is the supplied
inserted_span verbatim and whose replacement_span is shorter and
non-empty: {"rewrites":[{"original_span":"...","replacement_span":"..."}]}.
\end{lstlisting}

\subsection{Fluency judge (\texttt{fluency-judge-v2-rubric-100})}

The judge receives only the edited scenario text as the user message. It never sees
the choices or the foil.

\begin{lstlisting}[style=prompt]
Evaluate only the English fluency and readability of the supplied
scenario. Do not judge whether the facts are correct, whether the
scenario is emotionally appropriate, or which multiple-choice answer it
supports. Use this fixed scale: 90-100 means natural and grammatical with
no meaningful reading problem; 75-89 means understandable with only a
minor issue; 40-74 means noticeably awkward; 0-39 means seriously broken
or hard to understand. Do not invent a grammar error for a normal
sentence and do not penalise harmless style choices. Return JSON only,
using an integer score, for example: {"score":95,"issues":[]}. Return at
most five short issues.
\end{lstlisting}

\subsection{Fluency polish (\texttt{fluency-polish-v3-direct-span})}

The polish sees only the changed span and the surrounding context, never the choices
or the foil.

\begin{lstlisting}[style=prompt]
Delete only unnecessary words from original_span while keeping all
remaining words in their original order. Use context only to judge
readability. Do not add, replace, reorder, or inflect words, introduce
facts, change sentence boundaries, or rewrite the full context. Return
JSON with exactly two keys: original_span copied verbatim from the input
and one non-empty replacement_span. replacement_span must contain only
words and punctuation already present in original_span.
\end{lstlisting}
