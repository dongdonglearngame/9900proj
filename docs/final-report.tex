\section*{Executive Summary}
\addcontentsline{toc}{section}{Executive Summary}

We built a local web tool for studying how a small open-source language model answers
emotional-reasoning questions from EmoBench \cite{sabour2024}. A user loads a scenario,
sees the model's answer, chooses a different answer (we call it the \emph{foil}), and
runs a search strategy that tries to change the model's answer to that foil by editing
only the scenario text. This follows the general idea of counterfactual explanations:
show the smallest change to the input that changes the output
\cite{wachter2018,miller2019}.

The system contains a simple word-level baseline and three main counterfactual
strategies: \stratone{}, \strattwo{}, and \stratthree{}. All four run against the same
frozen target model through the same verification path, so their results can be
compared fairly.

We do not treat every answer change as a good explanation. The finished system
separates a \emph{mechanical flip} (the model changed its answer) from a
\emph{human-valid explanation} (reviewers agree the edit is a meaningful change), a
\emph{diagnostic finding} (the model reacted to wording, spelling, or a leaked answer
cue), and a valid \texttt{not\_found} result (no flip within the budget). This
distinction became central after our Sprint 2 experiments showed that a higher flip
rate can also mean larger, contradictory, or unhelpful edits.

In Sprint 3 we added a shared minimality stage and a fluency check, built a
discovery-focused variant of each main strategy, clarified the result labels in the
interface, and added accessibility settings. This report explains the final design,
shows the measured results, includes example outputs of good and bad quality, and
states clearly which goals were met and which were not. We present every flip as
evidence of model behaviour under a frozen test setup, not as proof of the model's
internal reasoning.

\section{Installation Manual}

The application is dockerised. Docker Compose builds and starts the backend (FastAPI)
and the frontend (React build served by nginx). Ollama stays on the host machine
because it manages the local language models; the project deliberately uses no paid
cloud API. The exact Python, Node, and package versions are pinned in the repository
(\texttt{backend/requirements.txt}, \texttt{frontend/package-lock.json}) and are listed
in the repository README, so the report only describes the steps to run.

\subsection{Prerequisites and Setup}

The machine needs Docker Desktop (or Docker Engine with Compose), Ollama, and the two
EmoBench data files (\texttt{EU.jsonl}, \texttt{EA.jsonl}), which are supplied
separately because the benchmark data is not committed to Git.

\begin{lstlisting}[style=terminal,language=bash]
# 1. Clone the repository and enter it
git clone <team-repository-url>
cd capstone-project-26t2-9900-f09c-almond

# 2. Start Ollama on the host and pull the frozen local model
ollama pull llama3.2:3b

# 3. Place EU.jsonl and EA.jsonl in data/raw/

# 4. Build and start the application
docker compose up --build -d

# 5. Load the EmoBench data into SQLite (one-off)
docker compose exec backend python -m app.scripts.load_emobench \
  --input /data/raw/EU.jsonl
docker compose exec backend python -m app.scripts.load_emobench \
  --input /data/raw/EA.jsonl
\end{lstlisting}

The frontend is then available at \url{http://localhost:5173} and the backend API
documentation at \url{http://localhost:8000/docs}. \texttt{docker compose down} stops
the application; the SQLite database lives in a named volume, so stored experiments
survive restarts. For development without Docker, the README also documents the
manual path (Python 3.11 virtual environment plus \texttt{npm run dev}).

\subsection{Major Components and Data Flow}

\begin{enumerate}
  \item The user selects an EmoBench scenario and the local model in the React
  interface.
  \item The backend asks the frozen target harness for the original answer. The target
  prompt is stateless and deterministic, and it never contains the foil.
  \item The user selects a foil and one strategy (Baseline, Strategy 1, Strategy 2, or
  Strategy 3, each with a strict or discovery variant where available).
  \item The strategy proposes scenario edits in its own way. Only the frozen target
  decides whether a candidate reaches the foil.
  \item A successful candidate then passes through shared minimality, fluency scoring,
  and risk labelling before metrics are stored and displayed.
  \item A search that uses up its budget without a flip is stored as
  \texttt{not\_found}. It is not turned into an error, and no explanation is invented.
\end{enumerate}

Because every strategy shares the same target function, prompt version, success rule,
budgets, and metric definitions, differences between strategies can only come from how
they search. That is what makes the comparison fair.

\section{Design Justifications}

We designed the system to support a controlled comparison of counterfactual search
strategies rather than to maximise the number of answer flips. This objective
required a frozen target interface shared by every strategy
(Section~\ref{sec:harness}) and strategy families based on distinct search
hypotheses (Section~\ref{sec:strategies}). It also required shared quality stages
that cannot independently classify a flip as a valid explanation
(Section~\ref{sec:quality}). The numerical settings in this chapter (the 0.60
changed-fraction cap, the 0.75 fluency threshold, the three-flip retention limit,
and the overbroad-span rule) are operational choices made during development, not
calibrated constants. Experiments and feedback from the client and tutor informed
each design decision. Table~\ref{tab:evolution} summarises the main changes across
the three sprints.

\subsection{Terminology and Outcome Categories}
\label{sec:terms}

We use the following terms throughout the report.

\begin{itemize}
  \item \textbf{Foil.} The foil is the alternative answer that the user wants the
  model to give. A search strategy may use the foil, whereas the target model never
  sees it.
  \item \textbf{Mechanical flip.} The frozen target model produces a mechanical flip
  when its answer after an edit matches the foil exactly. This result establishes
  that the answer changed. It does not establish that the edit provides a sound
  explanation.
  \item \textbf{Minimality.} Minimality measures edit size. We use the word-level
  edit distance between the original and edited scenarios, defined as the number of
  single-word insertions, deletions, and replacements needed to transform one into
  the other. We also record the changed-word fraction by dividing this count by the
  scenario length in words. Smaller edits are easier to read and analyse.
  \item \textbf{Fluency.} Fluency measures whether the edited text reads as natural
  English. A local judge model assigns a score (Section~\ref{sec:quality}), which we
  treat as a proxy rather than proof.
  \item \textbf{Semantic validity.} We use semantic validity to assess whether an
  edit meaningfully changes an event, outcome, relationship, or behaviour in the
  situation. Invalid edits include copying the answer into the text, replacing a
  word with a synonym, or contradicting the rest of the story. Our code flags clear
  cases. Human reviewers make the final judgement by labelling each flip Good,
  Acceptable, or Invalid and assigning reason codes.
  \item \textbf{Diagnostic finding.} A diagnostic finding is a verified flip that
  our checks classify as a model sensitivity, such as a near-synonym swap or answer
  leakage. We retain the finding as evidence about the model but do not publish it
  as an explanation.
  \item \textbf{Budget.} The budget sets the maximum number of target-model checks
  that a strategy may use for one scenario. Search and post-processing have separate
  capped allowances. We record every check so that the reported costs include all
  target-model checks.
\end{itemize}

These terms form a hierarchy because a mechanical flip is necessary for a
counterfactual explanation but is insufficient on its own. The automated system
assigns each run exactly one outcome category: mechanical flip (review needed),
diagnostic finding, not found, or failed. Section~4 reports every result using these
categories (Figure~\ref{fig:taxonomy}). The Good, Acceptable, and Invalid labels come
from the external blinded review protocol in Section~\ref{sec:review}. The pipeline
can only mark a flip as awaiting review. In the one fully reviewed run, all four
published flips were verified, fluent, and moderately sized, yet reviewers judged
every flip Invalid
(Section~\ref{sec:review}). This result provides empirical grounds for separating
automated categories from human judgement.

\subsection{Frozen Target Harness}
\label{sec:harness}

The system produces counterfactual explanations for a fixed black-box model. Every
strategy uses the same target prompt, decoding configuration, answer parser, and
cache contract. If strategies could change the target prompt, an observed difference
could arise from either the prompt or the edit. Appendix~\ref{app:prompts} provides
the full target prompt. We classify an edit as a flip when
\texttt{prediction.answer == foil}.

We also considered allowing each strategy to tune its own target prompt. Although
this alternative could increase individual flip rates, it would answer a different
question. The project compares which \emph{search procedure} finds better
counterfactuals, rather than which prompt makes the model easiest to move. Freezing
the target prompt, decoding configuration, parser, and cache reduces target-side
confounding, but some variance remains. The proposer samples at temperature 0.7 and
is not bit-for-bit repeatable. Section~4 therefore reports paired same-job
comparisons (Sections~\ref{sec:s1results} and~\ref{sec:s3results}) and uses the
single-run runtime table (Section~\ref{sec:runtime}) to illustrate the scale of the
costs rather than rank the strategies.

\subsection{Strategy Families}
\label{sec:strategies}

The four implemented families differ in the structure of the unit they modify: a
fixed word list, a free event-level rewrite, an importance-guided span infill, and a
single grounded concept intervention. We can therefore test distinct
search hypotheses instead of variants of one prompt. At the client's request, the
report uses the labels Strategies 1 to 3 and Baseline. Appendix~\ref{app:mapping}
maps these labels to the identifiers used in the code and stored experiment
metadata. Figure~\ref{fig:flows} presents the search process for each strategy.

The implemented scope differs from the proposal, which planned six strategy
families (internal identifiers S1 to S6). The delivered and evaluated release includes
four: S1 (the Baseline), S2 (Strategy~1), S4 (Strategy~2), and S6 (Strategy~3). Each
main family has a strict variant and a discovery variant. We did not implement the
control-code family (S3) or the population-based search family (S5), and no result in
this report uses either family. Both remain future work
(Table~\ref{tab:future}).

\paragraph{Baseline: word-level greedy search.}
The Baseline applies small word and phrase substitutions from a fixed list and
verifies each attempt. Because the candidates come from this list, the strategy uses
no LLM for generation. The resulting search is transparent and inexpensive, which
makes it a useful reference point, but its edits cannot express broader changes to
an event.

\paragraph{\stratone{}.}
A local proposer LLM reads the scenario, choices, and foil, then generates complete
rewrites that alter one event, outcome, relationship, or observable behaviour.
Deterministic guards reject candidates that break the structure, leak the answer, or
exceed the permitted edit size. The frozen target verifies every remaining
candidate. The Sprint 2 version (\emph{strict}) aims to change about three words and
permits at most six. The Sprint 3 \emph{discovery} variant removes this fixed word
cap while retaining a changed-fraction safety cap of 0.60. It keeps up to three
distinct verified flips and sends the best candidate to the shared quality pipeline.
The design draws on the zero-shot LLM counterfactual approach in
\cite{bhattacharjee2024} while keeping the target model and verification process
fixed.

\paragraph{\strattwo{}.}
This strategy first estimates the importance of each text span. It occludes one span
at a time, queries the frozen target for the resulting change in confidence for each
answer, and ranks the spans by importance. If confidence values are missing, the
strategy applies an answer-change heuristic and reports the resulting coverage
instead of replacing the missing values with zeros. The proposer LLM then replaces
content in the highest-ranked spans, and the frozen target verifies each result. This
method adapts importance-guided contrastive editing \cite{ross2021} to a black-box
setting without gradients. The discovery variant divides its fixed budget between
importance probes and candidate checks. It tests several high-ranked spans and mask
widths and records diagnostic candidates separately. Both variants are implemented
and unit-tested, and each completed a real-model smoke run. Their paired comparative
evaluation was not completed within the term, so the expected advantage remains a
design hypothesis rather than a measured result (Section~4).

\paragraph{\stratthree{}.}
This strategy changes one situational concept, such as time, place, relationship,
urgency, or outcome. The proposer LLM identifies an exact span and supplies a
replacement. Our code checks that the span occurs once before applying the edit,
preventing the LLM from rewriting the full story. The method draws on concept-level
counterfactual work \cite{gat2024}. We describe it as \emph{causal-inspired} because
changing one concept and observing the model constitutes an intervention on the
text. The intervention does not establish real-world causality. The discovery
variant adds an outcome concept class and permits a coherent multi-word replacement
span. It classifies an overbroad span (at least 12 tokens and more than half of the
scenario) as a diagnostic finding.

\paragraph{Strict and discovery variants.}
The variant split captures a design trade-off rather than a sequence of software
versions. Sprint~2 showed that a per-strategy word cap performed minimisation too
early. It discarded coherent event-level candidates before the shared minimiser
could assess them (Table~\ref{tab:prelim}). The discovery variants therefore search
more broadly within bounded budgets and safety caps, leaving shrinking, scoring, and
classification to the shared pipeline. In the paired dev-40 run, we observed broader
coverage alongside larger raw edits and more calls
(Table~\ref{tab:s1}). The strict variants remain the default and the comparison
baseline, preserving an auditable record of the Sprint~3 change.

\subsection{Shared Quality Pipeline: How Each Stage Works}
\label{sec:quality}

The proposal treated flip discovery and quality assessment as separate tasks, and
Sprint 3 implements that separation. The stages run in a fixed order. The frozen target
re-verifies every accepted transformation. Only the selected primary flip enters the
pipeline, while diagnostic flips remain separate as sensitivity evidence. A stage
that only scores, classifies, or records the current text makes no further target
call.

\paragraph{Minimality (greedy restoration).}
The minimiser takes a verified edited scenario and attempts to reduce the edit. It
aligns the original and edited text, identifies the changed regions, and restores
original content in stages, first by clause and then by word. After each proposed
restoration, the minimiser queries the frozen target. It keeps the restoration if the
answer remains the foil and reverses the change if the flip is lost. Processing stops
when no more content can be restored or the procedure reaches the post-processing
call cap. The result is a verified local minimum, with no guarantee that it is the
global minimum. We record the edit distance before and after minimisation and retain
both texts. A smaller final edit alone cannot establish that the original edit
captured a sound explanation.

\paragraph{Fluency (scored proxy).}
A separate local judge uses the same \texttt{llama3.2:3b} model with a fixed rubric
prompt, temperature 0, and prompt version \texttt{fluency-judge-v2-rubric-100}. The
judge reads only the edited scenario, without the choices or foil, and returns an
integer from 0 to 100. Scores from 90 to 100 indicate natural text, 75 to 89 a minor
issue, 40 to 74 noticeable awkwardness, and 0 to 39 broken text. We divide this
integer by 100 to obtain
$\text{score} = \text{judge integer} / 100 \in [0,1]$. A fluency assessment passes
when $\text{score} \ge 0.75$. This flag describes readability only, while semantic
validity requires separate review. A low or missing score does not suppress an
already verified flip on its own. If the judge fails or returns invalid output, we
record \texttt{not\_measured} and the reason rather than inventing a value. The score
remains a proxy. Section~\ref{sec:qualitative} documents a broken sentence that
passed, showing that a fluency pass cannot establish grammaticality.

\paragraph{One constrained polish.}
When the fluency score is low, the pipeline permits one polish attempt. The operation
may delete unnecessary words from the changed span while preserving the order of the
remaining words. It prohibits additions, replacements, reordering, inflection, and
any increase in edit distance. It must also preserve sentence boundaries and exclude
option letters, answer wording, and emotion labels. The pipeline keeps the polished
text only if the score increases and the text still flips the frozen target.
Otherwise, it restores the pre-polish result.

\paragraph{Risk flags and human review.}
Deterministic checks identify high-confidence problems, including exact or
morphological answer leakage, option references such as ``answer is C'', edits that
only replace a near-synonym or surface form, focal-person shifts, multi-concept spans,
and overbroad concept spans. We record flagged flips as diagnostic findings. Every
other flip remains ``mechanical flip, review needed'' until two reviewers assign
independent Good, Acceptable, or Invalid labels and reason codes. Each reviewer is
unaware of the other's label, and an adjudicator resolves disagreements. The review
protocol runs offline, outside the application, and its results appear in the
evaluation documents. In the one fully exercised review, the deterministic rules
flagged none of the four published flips (Section~\ref{sec:review}). This result
supports retaining human review as a mandatory final stage. Minimality and fluency
cannot make an invalid edit valid. For example, a short and grammatical answer leak
remains invalid.

\subsection{Evaluation Objectives and Criteria}

Our evaluation had to answer three questions. First, can a user actually carry out
the full research workflow in the tool. Second, how often does each strategy change
the frozen model's answer within a fixed search budget. Third, and most importantly,
are the edits it finds explanations that a person would accept. Sprint 2 already
showed us that these are different questions: an early prompt version found many
flips, but its average edit was about 16.7 words (Table~\ref{tab:prelim}), and we
could not defend edits of that size as targeted explanations. For this reason we did
not evaluate against a single success score. Instead we used the eight criteria in
Table~\ref{tab:criteria}. Flip discovery only measures search coverage. Minimality,
fluency, and semantic validity are the three edit-quality dimensions our client asked
us to define precisely, and their exact computation is given in
Section~\ref{sec:quality}. Efficiency, usability, and reproducibility judge the tool
itself rather than any single edit.

All quantitative measurements follow one rule: within a comparison, everything except
the strategy is frozen. The same pinned model, the same prompt versions, the same
questions, the same foil for every question, the same seed, and the same search
budget are used, and every verified flip then passes through the same quality
pipeline. If two variants produce different numbers under this rule, the difference
can only come from how they search. The rule also has a limit that we keep visible:
the strategies were evaluated on different question sets at different times, so we
only compare the strict and discovery variants within one set
(Sections~\ref{sec:s1results} and~\ref{sec:s3results}) and never rank strategies
against each other across sets.

For each criterion we also fixed in advance what counts as evidence. Flip discovery
and efficiency are read directly from run records: every run reports exactly one
outcome category and its search, post-processing, proposer, and total call counts,
and \texttt{not\_found} is stored as a real result rather than an error. Minimality
is reported as the raw versus final edit distance, and the final edit is a verified
local minimum, not a guaranteed global one. Fluency has a fixed pass line of
$\geq 0.75$ on the automatic score, and runs where the judge fails record
\texttt{not\_measured} instead of an invented value. Semantic validity is never
decided automatically; it requires two independent blinded reviewers
(Section~\ref{sec:review}). Usability and accessibility were checked by operating the
complete workflow described earlier with keyboard-only navigation, browser zoom, all
font sizes, themes, and both interface languages. Reproducibility means every
comparison records its commit, model digest, prompt versions, seed, question IDs,
foil plan, and budgets, so the same job can be repeated later. We deliberately did
not set a minimum flip rate as a success bar, because a low flip rate on a stable
model is itself a finding. What we required instead is that every run ends in an
honest category, and that no edit is called an explanation before it passes both the
automatic checks and human review.

\subsection{Result Categories}

The application separates automated execution outcomes from later human annotation.
Every completed run returned by the current API is reported as exactly one of four
automated categories:

\begin{itemize}
  \item \textbf{Mechanical flip -- review needed:} the target reached the foil, but
  quality has not been established yet;
  \item \textbf{Diagnostic finding:} a verified flip caused by lexical, formatting,
  focal-shift, evaluative-cue, or answer-leakage sensitivity and retained as evidence
  rather than a publishable counterfactual;
  \item \textbf{Not found:} no flip within the frozen budget, which is a real research
  result about model stability;
  \item \textbf{Failed:} an infrastructure or execution error, reported separately
  from bounded-search outcomes and kept visible in coverage reporting.
\end{itemize}

\emph{Valid explanation} is deliberately not an automatic application outcome. Human
review is conducted outside the web application using the frozen rubric and blinded
review sheets. Reviewers label a mechanical flip Good, Acceptable, or Invalid; only
Good and Acceptable labels count as human-valid in the external evaluation artifacts.
The current API, database schema, and interface do not store reviewer identities,
adjudication state, or a final human-valid category.

\subsection{Human Review Evidence}
\label{sec:review}

Blinded dual review is an offline evaluation protocol rather than a feature of the web
application. We exercised that protocol fully once during Sprint 3 using blinded
workbooks for an earlier Strategy 3 run. That run was later found to have a
contaminated control arm (the strict arm had received part of the Discovery
configuration), so its strict-versus-Discovery comparison is void and the 20 questions
are consumed; we keep the run only as review-process evidence and repeated the
mechanical comparison on the new frozen set above. Two reviewers independently
labelled all four published flips with strategy identity hidden, agreed on 3 of 4
validity labels, and adjudicated the one disagreement. The final labels were 4 Invalid
out of 4, with reason codes including grammar, irrelevant change, near-synonym,
contradiction, evaluative cue, excessive edit, and model sensitivity. The reviewer
sheets and reconciled labels are external evaluation artifacts; they are not persisted
by the current application.

This is an informative negative result. All four edits had exact single-concept
metadata, verified flips, passing fluency scores, and moderate edit sizes, and human
reviewers still judged all four invalid as explanations. Mechanical checks alone are
not enough, which is why the evaluation methodology requires a separate human-review
stage.

\subsection{Qualitative Analysis: Good and Bad Examples}
\label{sec:qualitative}

Numbers alone hide what the edits actually look like, so here are real outputs, quoted
from stored artifacts, with our assessment.

\paragraph{Provisionally acceptable (Strategy 1, holdout question 107).}
The original scenario ends ``\ldots the result was \emph{the expected one}.'' The edit
replaces this with ``\ldots the result was \emph{unusually accurate}.'' The model's
answer changed to the foil. The edit changes the real outcome of the event, stays
grammatical, and does not mention any answer text, so the reviewer marked it
provisionally acceptable. This is the behaviour we want the tool to find.

\paragraph{Invalid: surface-level colour change and model sensitivity (Strategy 1,
holdout question 132).}
The edit changed one word, ``pale'', to ``green'', in a description of someone's face.
The model flipped, but no fact about the situation changed. This is lexical
instability of the model, so the provisional human review marked it Invalid with a
model-sensitivity reason. This historical strict-strategy result predates the
Discovery diagnostic queue, so we do not claim that the application automatically
classified it as a diagnostic outcome.

\paragraph{Invalid: cue made more explicit (Strategy 3 discovery, evaluation
question 162).}
The edit replaced ``his face squished up'' with ``a look of distaste on his face'',
and the model moved from Embarrassment to Annoyance. The automatic checks flagged
nothing and fluency scored 0.90, but content review found the modified clause is a
sentence fragment, the ``emotional intensity'' concept label does not match what the
replacement actually does, and the change mainly makes an already negative cue more
explicit rather than changing the situation. Provisionally invalid; blinded labels
pending. It is still useful evidence that the model is sensitive to the explicit word
``distaste''.

\paragraph{Quality issue flagged by the fluency proxy (Strategy 1 discovery, dev
question 161).}
Discovery found a coherent raw rewrite: ``It said there is a restaurant famous for its
rude customer service'' became ``She had already heard about the infamous waiters who
often insult customers''. Minimality then reduced the 12-word edit to 2 words, leaving
``She said already is a restaurant famous\ldots'', which is broken English. The
fluency judge scored it 0.62, below the 0.75 threshold, so the quality issue was
flagged and reported. A low score does not erase the verified mechanical result; it
marks the result for cautious interpretation and possible bounded polishing. This
example is why we keep the raw, minimal, and final versions all visible.

\paragraph{Quality issue missed by the fluency proxy (Strategy 1 discovery, dev
question 121).}
On another question, minimisation of a larger rewrite produced ``\ldots Vivian's leg
began shake uncontrollably'', which drops the word ``to'' and is ungrammatical, yet
the judge scored it 0.83 and passed it. This false pass is direct evidence that the
automatic fluency score is a proxy that can be wrong in both directions, and it is one
reason human review remains mandatory.

\subsection{Which Objectives Were Met}

Against the criteria in Table~\ref{tab:criteria}, the functional experiment and
comparison workflow, automated outcome categories, flip discovery, minimality
processing, fluency measurement, and efficiency metrics are implemented. The
interface also implements Simplified Chinese, font scaling, system/light/dark themes,
reduced-motion handling, enhanced focus, and a magnifier. These are implementation
outcomes; the repository does not contain a formal frontend usability or accessibility
test suite, so they are not presented as a completed user-study result.

Reproducibility is supported by frozen question-ID lists, evaluation documents,
checksums, Git commits, and retained external artifacts. However, the generic
experiment-run record does not automatically store every model digest, seed, Ollama
version, proposer prompt, or machine detail. Fluency is measured, but its reliability
is only partly established: one false pass and one correct flag are documented above.
Semantic validity remains the least complete objective. The offline dual-review
protocol was completed for one consumed run, while the newest Strategy 1 and Strategy
3 labels are pending. Strategy 2 has smoke-level execution evidence but no full paired
evaluation, and the current application does not persist reviewer labels or
adjudication outcomes.

\section{Limitations and Future Work}

\subsection{Limitations}

\begin{itemize}
  \item \textbf{Small local model.} The default 3B model runs on CPU laptops but has
  limited emotional reasoning, instruction following, and editing ability. Observed
  sensitivities may be specific to this model.
  \item \textbf{Black-box evidence.} A counterfactual shows the output changed when
  the input changed. It does not reveal internal reasoning or prove causality, and we
  label Strategy 3 causal-inspired for exactly this reason.
  \item \textbf{Mechanical versus valid flips.} Minimality and fluency cannot turn an
  answer leak, contradiction, or irrelevant cue into a valid explanation. On the one
  fully reviewed run, all four published flips were judged invalid.
  \item \textbf{Human review scale.} Two-reviewer validity labels exist for one
  consumed run; the blinded labels for the newest Strategy 1 and Strategy 3 flips are
  still pending, so all newer validity statements are provisional.
  \item \textbf{Automatic quality proxies.} The fluency judge false-passed a broken
  sentence (0.83) and the risk rules flagged none of the four human-invalid flips, so
  neither replaces review.
  \item \textbf{Minimality side effects.} Greedy restoration sometimes removes
  connective words and produces fragments; raw and final texts are both kept visible
  to compensate.
  \item \textbf{Incomplete comparisons.} Strategy 2 has only smoke-level evidence, and
  a single all-strategy controlled holdout matrix was not run within the term; the
  per-strategy paired comparisons above use different sets and must not be compared
  against each other.
  \item \textbf{Run variability.} The proposer runs at temperature 0.7 and is not
  bit-for-bit repeatable across local runs even with a fixed seed, so paired
  same-job comparisons are reported and repeated-run variance remains unmeasured.
  \item \textbf{Evaluation scope.} EmoBench is a benchmark, not a clinical setting.
  The tool analyses model behaviour and must not be used to provide mental-health or
  medical advice.
  \item \textbf{Language setting.} The interface language switch translates the
  interface only; translating scenarios would change the input being evaluated.
\end{itemize}

\section{Conclusion}

We delivered a working, dockerised local tool and a controlled way to study
counterfactual editing strategies on emotional-reasoning questions. The main result is
not one high flip rate. It is a reproducible workflow that shows when a frozen model's
answer can be changed, how small and readable the change is, what kind of change it
was, and whether people judge it a useful explanation. On our measurements, discovery
search finds clearly more mechanical flips than the strict Sprint 2 baseline on
development data (25\% versus 10\% for Strategy 1) at a higher edit-size and call
cost, a harder unenriched set yields very few flips for Strategy 3 (1/20), and the one
fully reviewed run showed that verified, fluent, small edits can still all be invalid
as explanations. The honest separation of valid, diagnostic, not-found, and failed
outcomes, kept visible from the code through to the interface, is what makes those
statements trustworthy, and it is the part of this project we would keep first.

\section{Prompt Texts}
\label{app:prompts}

Every prompt sent to an LLM is versioned, and the version string is stored with each
experiment run. The instruction texts below are quoted from the code at the release
commit. Each proposer prompt is accompanied by a JSON user message containing the
scenario, choices, original answer, foil, requested count, and previously failed
attempts; the target and fluency prompts receive only what is shown.

\subsection{Frozen target prompt (\texttt{target-v2-chat-dynamic-choices})}

The system message is built from the actual choice letters (two to six choices are
supported):

\begin{lstlisting}[style=prompt]
You answer multiple-choice emotional reasoning questions. Return only one
letter A, B, C, or D. Do not explain.
\end{lstlisting}

The user message contains only the scenario and the choices. It never contains the
foil, the ground truth, or any strategy information:

\begin{lstlisting}[style=prompt]
Scenario
<scenario text>

Choices
A. <choice text>
B. <choice text>
...

Answer with exactly one letter.
Answer
\end{lstlisting}

\subsection{Strategy 1 strict proposer (\texttt{s2-proposer-v5-\allowbreak coherence-\allowbreak checklist})}

\begin{lstlisting}[style=prompt]
You propose minimal counterfactual rewrites for emotion-reasoning
multiple-choice scenarios. You may see the target foil, but the frozen
target model will not. Change an underlying event, outcome, relationship,
or observable behaviour rather than directly naming or paraphrasing the
target emotion or answer. Modify exactly one existing sentence and do not
append, prepend, split, or merge sentences. Prefer changing no more than
3 words and never change more than 6 words. Preserve the surrounding
facts, actors, tense, grammar, and narrative coherence. Rewrite only the
scenario, keep it fluent and realistic, do not mention option letters,
and do not copy or morphologically derive any option answer text in the
scenario. Do not add a sentence or clause whose purpose is to state how a
person feels; express the change through an observable event, outcome,
relationship, or behaviour. Do not propose an edit that makes unchanged
sentences contradict the modified fact. Keep the changed sentence about
the same focal person or event and preserve at least one meaningful
content word from that sentence. Never replace a focal person's outcome
with a reaction by the crowd or another bystander. Before returning each
rewrite, silently check every unchanged sentence for references to a fact
the rewrite removed. [quality examples omitted for space; they show one
good three-word outcome edit and three bad patterns to avoid]
Return exactly the requested number of distinct rewrites and use a
different change mechanism where possible. Treat avoid entries as prior
failures and do not repeat them. Return JSON only; modified_scenario is
required and changed_span, change_type, and rationale are optional:
{"rewrites":[{"modified_scenario":"...","changed_span":"...",
"change_type":"event|outcome|relationship|behaviour","rationale":"..."}]}.
\end{lstlisting}

\subsection{Strategy 1 discovery proposer
(\texttt{s2-proposer-v8-2-\allowbreak discovery-\allowbreak focused-event})}

\begin{lstlisting}[style=prompt]
You search for counterfactual scenario edits for an emotion-reasoning
multiple-choice task. You may see the target foil, but the frozen target
model will not. Rewrite only the scenario and keep every answer choice
unchanged. Make one focused, coherent change to an underlying event,
outcome, relationship, or observable behaviour that could support the
target answer. Keep the change concise, but do not force it into a fixed
word count when a larger local change is needed for coherence. Return the
complete scenario for every rewrite, not only the changed sentence. Keep
exactly the same number and order of sentences, copy every unchanged
sentence word-for-word, and replace only one existing sentence in place.
Do not append, prepend, split, or merge sentences. Preserve the focal
person, tense, unrelated facts, grammar, and references from unchanged
sentences. Do not state an emotion as a shortcut, mention an option
letter, or copy answer-option wording into the scenario. Treat avoid
entries as prior failures and propose distinct mechanisms where possible.
The rewrites array must contain exactly <count> distinct objects; do not
stop after fewer than <count>. The top-level object must contain only the
rewrites key. Never echo input keys such as scenario, choices,
constraints, count, foil, or avoid. Replace every placeholder in this
exact output shape and return JSON only: {"rewrites":[
{"modified_scenario":"<complete scenario rewrite 1>","changed_span":
"<changed text>","change_type":"event|outcome|relationship|behaviour",
"rationale":"<brief reason>"}, ...]}
\end{lstlisting}

\subsection{Strategy 2 infill proposer (\texttt{s4-infill-v1})}

\begin{lstlisting}[style=prompt]
You fill masked spans in emotion-reasoning multiple-choice scenarios.
You may see the target foil, but the frozen target model will not.
Only replace each [MASK] span. Preserve every unmasked character exactly,
keep the final scenario fluent and realistic, do not mention option
letters, and do not copy any option answer text into the scenario.
Return JSON only:
{"rewrites":[{"modified_scenario":"...","rationale":"..."}]}.
\end{lstlisting}

\subsection{Strategy 3 strict proposer (\texttt{s6-concept-v2-grounded-diverse})}

\begin{lstlisting}[style=prompt]
You propose causal-inspired concept interventions for emotion-reasoning
scenarios. Each edit must change exactly one allowed concept through one
contiguous span replacement while keeping every other fact and concept
fixed. Copy original_span exactly from the scenario. Return only the
replacement, not a rewritten full scenario. Do not mention option letters
or copy any option answer text. Return exactly the requested number of
edits. Within this response, use different concept classes and original
spans where possible. Do not repeat any concept/span/target tuple in
used_edits or avoid. Return JSON only:
{"edits":[{"concept_class":"time","original_span":"...",
"replacement_span":"...","source_value":"...","target_value":"...",
"rationale":"..."}]}.
\end{lstlisting}

\subsection{Strategy 3 discovery proposer (\texttt{s6-concept-v3-discovery-first})}

\begin{lstlisting}[style=prompt]
You propose causal-inspired concept interventions for emotion-reasoning
scenarios. Treat one coherent situational concept intervention, not a
fixed token count, as the unit of change. A multi-word replacement is
allowed when needed to express that one concept clearly. Each edit must
change exactly one allowed concept through one contiguous span
replacement while preserving the focal actor, focal event, and every
unrelated fact. Copy original_span exactly from the scenario. Return only
the replacement, not a rewritten full scenario. Do not mention option
letters or copy any option answer text. Return exactly the requested
number of edits. Prefer unused concept classes and original spans, and do
not repeat any concept/span/target tuple in used_edits or avoid. Return
JSON only: {"edits":[{"concept_class":"time","original_span":"...",
"replacement_span":"...","source_value":"...","target_value":"...",
"rationale":"..."}]}.
\end{lstlisting}

\subsection{Strategy 3 grounding repair (\texttt{s6-concept-repair-v1})}

\begin{lstlisting}[style=prompt]
Repair only the grounding of one causal-inspired concept edit. Return
exactly one edit with an original_span copied verbatim from the scenario
that occurs exactly once. Preserve the supplied concept_class,
replacement_span, source_value, and target_value; do not invent a
different intervention or rewrite the full scenario. Do not mention
option letters or copy answer text. Return JSON only in the same edits
schema.
\end{lstlisting}

\subsection{Minimality span shrink (\texttt{postprocess-\allowbreak inserted-span-\allowbreak shrink-v2})}

\begin{lstlisting}[style=prompt]
Reduce one inserted span by deleting unnecessary words only. Keep the
remaining words in their original order; do not paraphrase or add any new
word or fact. Do not rewrite the rest of the scenario, mention option
letters, name the target answer, or add emotion labels. Return JSON only
with exactly one rewrite whose original_span is the supplied
inserted_span verbatim and whose replacement_span is shorter and
non-empty: {"rewrites":[{"original_span":"...","replacement_span":"..."}]}.
\end{lstlisting}

\subsection{Fluency judge (\texttt{fluency-judge-v2-rubric-100})}

The judge receives only the edited scenario text as the user message. It never sees
the choices or the foil.

\begin{lstlisting}[style=prompt]
Evaluate only the English fluency and readability of the supplied
scenario. Do not judge whether the facts are correct, whether the
scenario is emotionally appropriate, or which multiple-choice answer it
supports. Use this fixed scale: 90-100 means natural and grammatical with
no meaningful reading problem; 75-89 means understandable with only a
minor issue; 40-74 means noticeably awkward; 0-39 means seriously broken
or hard to understand. Do not invent a grammar error for a normal
sentence and do not penalise harmless style choices. Return JSON only,
using an integer score, for example: {"score":95,"issues":[]}. Return at
most five short issues.
\end{lstlisting}

\subsection{Fluency polish (\texttt{fluency-polish-v3-direct-span})}

The polish sees only the changed span and the surrounding context, never the choices
or the foil.

\begin{lstlisting}[style=prompt]
Delete only unnecessary words from original_span while keeping all
remaining words in their original order. Use context only to judge
readability. Do not add, replace, reorder, or inflect words, introduce
facts, change sentence boundaries, or rewrite the full context. Return
JSON with exactly two keys: original_span copied verbatim from the input
and one non-empty replacement_span. replacement_span must contain only
words and punctuation already present in original_span.
\end{lstlisting}
